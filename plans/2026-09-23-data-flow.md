Let's plan the entire data strategy for this app between the watch and the phone, including any reply handling.

To start, we need to determine the types of data that are transmitted and the direction they are transmitted.

I believe these are the data types and directions:

* Start round [Phone -> Watch] or [Watch -> Phone]
* End round [Phone -> Watch] or [Watch -> Phone]
* New GPS data [Watch -> Phone]
* Change current hole [Phone -> Watch] or [Watch -> Phone]
* Add mark [Phone -> Watch] (this updates the `Previous` display on the watch)
* Modify mark [Phone -> Watch] (this updates the `Previous` display on the watch)
* Delete mark [Phone -> Watch] (this updates the `Previous` display on the watch)

Some of these message must be acknowledged before either app continues processing:

* Start round must ensure that the phone and watch are both in an active round with a course
* End round must ensure that the watch has synced all the GPS data to the phone before the round is ended, regardless of where this state transition starts (phone or watch)

When the hole is changed, the other device might have a delay before its state is changed. This means that if the hole is changed on the phone the watch might still be collecting GPS data and associating it with the wrong hole. This is solved by having the phone attach a timestamp to this message and the watch can fix the GPS data it collected after this timestamp to be on the correct hole.

When the GPS data is sent, it doesn't need to always make it to the phone. However, the phone and watch should have a mechanism to ensure that all the data between the devices is consistent. This needs some type of id system and a way for the phone to ask the watch for missing data. If the watch uses a simple incrementing integer then it should be easy to reconcile. Unless the iOS or watchOS APIs include a method of ensuring delivery without any timing issues or reply handling issues, we will have to design our own solution for this. GPS data is fully ordered though, so a simple counter should work if we need to implement this.

GPS data should be sent as frequently as possible without impacting battery life. If there is an API that allows us to add messages to a queue, then we can send the GPS data every time it is collected.
